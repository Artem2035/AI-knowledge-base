# Документация: `llm/prompts/*` — статичные системные инструкции ролей

> Reference-док, покрывающий ВЕСЬ подпакет `llm/prompts/` (5 файлов) одним
> документом — см. `_index.md` за обоснованием (каждый файл мал, отдельный
> подпакет `_index.md` для них избыточен). Схемы, под которые пишутся эти
> промпты — `schemas.md`. Сами роли, которые их вызывают — `../roles/`.

**Общий принцип пакета.** Статика (системная инструкция роли, не меняется
от вызова к вызову в рамках задачи) отделена от динамики (собирается в
`roles/*.py` из конкретных `Plan`/`Evidence`/`DraftNote` на каждый вызов).
Это важно для Groq prompt caching — ОДНА И ТА ЖЕ строка на все вызовы
задачи не ломает кэш (см. `groq_client.md §4`, `CacheObservability`).

## 0. `llm/prompts/__init__.py`

Пустой файл-маркер пакета.

## 1. `llm/prompts/outline_planner.py`

### `OUTLINE_PLANNER_SYSTEM_INSTRUCTION: str`

Системная инструкция роли Planner (`role="outline_planner"`). Ключевые
правила (из текста инструкции):
1. Заметка = самостоятельная концепция, понятная без чтения других заметок
   — не дробить на заметки то, что имеет смысл только в контексте другой
   заметки (это подпункт, а не отдельная заметка).
2. Число заметок и подпунктов определяется ИСКЛЮЧИТЕЛЬНО полнотой темы — не
   подгонять под круглое число; тема может объективно требовать 20-30
   подпунктов в одной заметке, дальнейшая генерация текста по подпунктам НЕ
   зависит от их количества (см. `chunking.md §2`,
   `batch_for_quality_and_budget`).
3. Для каждого подпункта — короткое техзадание (`covers`), а НЕ сам текст.
4. Логическая последовательность подпунктов: определение/контекст →
   механизм → применение → ограничения/сравнение с альтернативами —
   используя ТОЛЬКО уместные для темы пункты.

Плюс языковое правило: русский, кроме общепринятых технических терминов
(SQL, Python, RAG), которые не переводятся.

**Используется в:** `roles/outline_planner.py::build_plan`
(`../roles/outline_planner.md`).

## 2. `llm/prompts/critic.py`

### `FEW_SHOT_EXAMPLES: str`

Конкатенируется в конец `SYSTEM_INSTRUCTION`. Два развёрнутых примера
вердиктов, задающих "уровень строгости" критика:
- **`verdict='rewrite'`:** заметка с дублирующим по смыслу разделом
  ("Применение" пересказывает "Механизм") И придуманной точной цифрой,
  не встречающейся ни в одном evidence — с образцом конкретного,
  адресуемого `feedback`.
- **`verdict='ok'`:** заметка структурирована по заголовкам плана, факты
  отражены своими словами без искажений; МЕЛКАЯ стилистическая
  шероховатость — НЕ повод для `rewrite`.

Ключевое отличие, проговорённое в тексте: `rewrite` — за КОНКРЕТНУЮ,
адресуемую проблему; НЕ `rewrite` — за стилистические предпочтения, длину
предложений, выбор синонимов.

### `SYSTEM_INSTRUCTION: str`

Системная инструкция роли Critic (`role="critic"`, ревью УЖЕ НАПИСАННОЙ
заметки — не сверяет с текстом источника, сверять не с чем ни в
`RESEARCH_MODE=knowledge`, ни в текущей интеграции для web). Проверяет:
1. внутреннюю согласованность (нет ли противоречий внутри текста);
2. полноту относительно списка фактов;
3. структуру и ясность изложения (повторы, вода, оборванные мысли);
4. отсутствие ЯВНО добавленных точных деталей (чисел, дат, версий),
   которых не было среди переданных фактов;
5. полноту покрытия заголовков плана (все заявленные разделы `##` должны
   присутствовать и быть содержательно раскрыты).

Явно проговаривает: у критика НЕТ доступа к внешним источникам — не
пытаться проверять фактическую точность против реального мира. Итог:
`verdict='ok'`, если заметка хороша; `verdict='rewrite'` с КОНКРЕТНЫМИ
замечаниями — если есть существенные проблемы; НЕ придираться по мелочам.

`SYSTEM_INSTRUCTION = "..." + FEW_SHOT_EXAMPLES`.

**Используется в:** `roles/critic.py::review_draft` (`../roles/critic.md`).

## 3. `llm/prompts/elaborator.py`

### `SYSTEM_INSTRUCTION: str`

Системная инструкция роли Elaborator (`role="elaborator"`, только
`RESEARCH_MODE=knowledge`). В отличие от Extractor, здесь НЕТ входного
текста источника — модель раскрывает подтему из СОБСТВЕННЫХ знаний.
Формулировка НАМЕРЕННО требует явно помечать неуверенность. Ключевые
правила:
- раскрыть КАЖДЫЙ раздел ОТДЕЛЬНО, строго по техзаданию (`covers`), не
  путая материал разных разделов между собой;
- писать на русском, кроме общепринятых терминов;
- **честность:** не выдумывать точные числа/даты/версии/статистику/имена
  авторов, если не уверена модель — лучше сформулировать обобщённо;
- `confidence` оценивается ЧЕСТНО: высокий (>0.8) — только для
  устоявшихся, общеизвестных фактов; для деталей, которые могут быть
  неточными — снижать `confidence` и коротко пояснять в `critic_note`;
- если у раздела есть существенно разные трактовки в индустрии — отметить
  это явно, а не выбирать один вариант как единственно верный;
- каждое утверждение атомарно (одна мысль);
- для каждого факта указать `unit_index` — номер раздела в квадратных
  скобках, к которому он относится.

**Используется в:** `roles/elaborator.py::_elaborate_batch`
(`../roles/elaborator.md`).

## 4. `llm/prompts/vault_analyst.py`

**Назначение.** Используется ТОЛЬКО для "серой зоны" схожести
(`tools/dedup.py::classify_similarity`, `../tools/dedup.md`).

### `SYSTEM_INSTRUCTION: str`

Инструкция роли Vault Analyst для решения "это та же концепция?"
(`role="vault_dedup"`). Дана концепция/факт из нового исследования и
существующая заметка Vault (заголовок, теги, краткое содержание).
Определить: та же концепция (стоит переиспользовать/дополнить), или разные,
самостоятельные концепции (нужна отдельная новая заметка). Главное правило:
НЕ ПЛОДИТЬ ДУБЛИКАТЫ — если модель сомневается между `'reuse'` и
`'distinct'`, выбирать `'extend'` (дополнить существующую заметку новым
материалом).

**Используется в:** `roles/vault_analyst.py::_resolve_ambiguous`
(`../roles/vault_analyst.md`).

### `FOLDER_SYSTEM_INSTRUCTION: str`

Инструкция роли Vault Analyst для распределения по папкам
(`role="folder_assignment"`). Даны: список существующих папок Vault, папка
по умолчанию для темы, список НОВЫХ заметок (заголовок + разделы). Для
КАЖДОЙ заметки указать её индекс и папку — либо ТОЧНОЕ имя одной из
существующих папок, либо папку по умолчанию. Явный запрет: НИКОГДА не
придумывать новые папки, которых нет в списке и которые не являются папкой
по умолчанию.

**Используется в:** `roles/vault_analyst.py::_assign_folders_batch`. Код
дополнительно ПРИНУДИТЕЛЬНО проверяет это правило после ответа (safety net,
см. `schemas.md §6`) — инструкция промпта НЕ является единственной защитой
от галлюцинированных папок.

## 5. `llm/prompts/synthesizer_writer.py`

### `FORMATTING_GUIDANCE: str`

Вынесенный в ОТДЕЛЬНУЮ константу блок про форматирование (Obsidian Flavored
Markdown) — переиспользуем отдельно, и чтобы правки форматирования не
задевали остальную часть инструкции. Принцип: элементы форматирования
(callout, списки, код) — это ИНСТРУМЕНТЫ ПО СМЫСЛУ, а НЕ обязательный
чек-лист на каждую заметку. Прежняя версия промпта требовала фиксированную
структуру — модель добавляла притянутые списки из ОДНОГО пункта и пустые
предупреждения там, где по содержанию их не было (подгоняла материал под
форму вместо обратного) — эта проблема стала причиной переписать промпт
без обязательных элементов.

Конкретное содержание: `> [!type] Заголовок` callout-ы (`abstract` — резюме
перед деталями, не для короткой заметки; `warning` — частая
ошибка/неочевидное поведение; `tip` — практический совет; `info` — важное
уточнение контекста); списки (нумерованный — только реальная
последовательность шагов; маркированный — перечисление однородных
фактов/вариантов); `**жирный**` — ключевые термины; `` `код` `` — имена
функций/методов/путей; курсив — смысловой акцент, умеренно; блоки
` ```язык ` — только для реально иллюстрирующего примера; LaTeX (инлайн
`$x^2$`, блок-формула двойными `$$` на отдельных строках, НЕ оборачивать в
` ``` `) — только для объективно математических/технических тем.

### `WRITE_SYSTEM_INSTRUCTION: str`

Системная инструкция роли Obsidian Writer (`role="synthesizer_write"`).
Ключевые правила:
- пишет ОДНУ заметку по плану (заголовок/action/папка заданы, НЕ
  обсуждаются); для `action='create'`: `tags`, `body_md`, `links_out`; для
  `action='update'`: `append_section` — только НОВЫЙ материал, НЕ повторять
  существующее содержимое;
- объём: целевой диапазон слов задаётся В ПРОМПТЕ (динамически, не здесь);
  фактов меньше, чем нужно для объёма — писать короче и честно (минимум 3
  содержательных абзаца), не растягивать повторами;
- + `FORMATTING_GUIDANCE` (вставлена f-строкой внутрь);
- ссылки (`links_out`) — только заголовки заметок Vault (НИКОГДА не URL),
  точно как в переданном списке (включая дефисы);
- ЗАПРЕЩЕНО: свой раздел/предложение "См. также"/"Related notes" внутри
  `body_md`/`append_section` — секцию "## Связанные заметки" система
  формирует САМА из `links_out` (`tools/markdown_tools.md`), дублирование
  ломает вывод; другие ключи YAML frontmatter (кроме `title`/`tags`/
  `created`) — не предлагать, система их игнорирует;
- язык: русский, кроме общепринятых терминов; НЕ копировать текст источника
  дословно.

**Используется в:** `roles/synthesizer_writer.py::write_note`
(`../roles/synthesizer_writer.md`), как дефолт для `system_instruction`.

### `MERGE_AWARENESS_GUIDANCE: str`

Добавляется к `WRITE_SYSTEM_INSTRUCTION` ТОЛЬКО когда
`settings.enable_draft_merging=True`. Writer НЕ ЗНАЕТ, с КЕМ КОНКРЕТНО
заметка будет объединена (решается пользователем в самом конце, см.
`../staging/draft_merge.md`), но может заранее писать так, чтобы объединение
с ЛЮБЫМИ соседями по плану проходило чище. Правила:
- НЕ писать шаблонное вступление ("В этой заметке рассмотрим...") или
  заключение ("Подводя итог...") — при объединении такие фразы повторяются
  на каждый раздел;
- если заметка предполагает БАЗОВОЕ определение общей темы плана — дать
  его КОРОТКО, одной фразой, и сразу переходить к специфике именно ЭТОЙ
  заметки;
- оставаться строго в рамках заявленного заголовка, не отклоняться в
  объяснение смежных концепций.

Один и тот же СТАТИЧНЫЙ вариант системного промпта на ВСЮ задачу — важно
для Groq prompt caching.
