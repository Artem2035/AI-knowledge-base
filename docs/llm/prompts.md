# Документация: `llm/prompts/*` — статичные системные инструкции ролей

> Reference-док для всего подпакета `llm/prompts/` (5 файлов). Схемы — `schemas.md`. Роли — `../roles/`.

**Общие принципы.**
- Статика (инструкция роли) отделена от динамики (промпт, который собирает роль из `Plan`/`SectionDraft`). Одна и та же строка на все вызовы задачи не ломает Groq prompt caching (`groq_client.md §4`). Поэтому инструкции Elaborator строятся **один раз на домен** при импорте, а не на каждый вызов.
- Инструкции написаны **на английском**, а заметки пользователя должны быть на русском. Это обеспечивает `LANGUAGE_RULE` (§0). Имена полей и enum-значения схемы не переводятся: суффикс про это добавляет `GroqClient._build_response_format_and_system`.
- Защитная проверка языка результата — `validation/markdown_validator.py` (`note_language_mismatch`).

## 0. `llm/prompts/common.py`

### `LANGUAGE_RULE: str`
«Write all text values in Russian; keep technical terms untranslated (SQL, Python, RAG, etc.)». Дописывается в конец инструкций Planner, Elaborator, Annotator и Vault Analyst (`SYSTEM_INSTRUCTION`).

## 1. `llm/prompts/outline_planner.py`

### `OUTLINE_PLANNER_SYSTEM_INSTRUCTION: str`
Роль Planner (`role="outline_planner"`). Правила:
1. заметка — самостоятельная концепция, понятная без других заметок; то, что имеет смысл только в контексте другой, — подпункт;
2. число заметок и подпунктов определяется только полнотой темы (допустимо 20–30 подпунктов в заметке);
3. для каждого подпункта — короткое техзадание `covers`, не текст;
4. логический порядок подпунктов (определение/контекст → механизм → применение → ограничения), только уместные пункты;
5. классификация `domain`: `technical` / `humanities` / `life_management`, при неоднозначности — ближайший;
6. `kind` каждого подпункта — только из списка выбранного домена (или `other`), не навязывать все виды в каждую заметку;
7. `summary` — один абзац (4–6 предложений) для читателя, не знакомого с темой: что это, зачем, что охватывает набор заметок и как они связаны; сплошной текст без списков и заголовков, без чисел, дат, версий и имён, в которых нет уверенности.

Плюс `LANGUAGE_RULE`. Используется `roles/outline_planner.py::build_plan`.

## 2. `llm/prompts/elaborator.py`

### `get_system_instruction(domain: str) -> str`
Возвращает статичную инструкцию Elaborator для домена; неизвестный домен → `technical`. Собрана из блоков:

- `_COMMON` — общая часть: нет внешних источников, писать готовый markdown **каждого раздела отдельно** по `covers` и `kind`.
  - **Формат раздела:** `markdown` без собственного заголовка (код добавит `## …`); внутри предпочтительно `##`, `###`/`####` только при необходимости, никогда `#` и не глубже `####`; без вступлений и заключений; не повторять то, за что отвечают соседние разделы (их заголовки даны), базовое определение — одной фразой.
  - **Obsidian Markdown по смыслу, а не по шаблону:** маркированный список для однородных фактов, нумерованный — только для реальной последовательности, таблица для сравнения по критериям, `**жирный**` для ключевых терминов, `` `код` `` для имён, fenced-блок с языком (всегда закрывать), LaTeX, callout'ы `[!warning]`/`[!tip]`/`[!info]` только где содержание действительно требует. Пустой или натянутый элемент хуже его отсутствия.
  - **Код:** рабочий и минимальный, с нужными импортами, без выдуманных функций, параметров и API; сомнительные детали опускать.
  - **Честность (нет внешней проверки):** не выдумывать числа, даты, версии, статистику, имена; при неуверенности формулировать обобщённо и ставить `needs_check=true`.
  - **Ответ:** ровно один элемент на раздел, `unit_index` — номер раздела в квадратных скобках.
- `_KIND_RULES[domain]` — правило для каждого `kind` домена (например, `parameters`: список `` `имя` — смысл, значение по умолчанию (только если уверены) ``, только существующие параметры; `pitfalls`: 2–5 конкретных ошибок, уместен warning-callout; для `life_management.checklist`: `- [ ] пункт`).
- `_DOMAIN_RULES[domain]` — отдельное правило домена: `technical` — точность важнее широты; `humanities` — **без** прямых цитат, точных дат, названий трудов и имён, если нет уверенности, не выдавать одну трактовку за единственную; `life_management` — конкретно и практично, без выдуманной статистики и ссылок на исследования.
- `LANGUAGE_RULE`.

Используется `roles/elaborator.py::elaborate_outline`. Внутренний кэш: `_INSTRUCTIONS: dict[str, str]`, один элемент на ключ `_KIND_RULES`.

## 3. `llm/prompts/annotator.py`

### `SYSTEM_INSTRUCTION: str`
Роль Annotator (`role="annotator"`). Вход — дайджесты нескольких написанных заметок (заголовок + заголовки разделов с началом текста); опираться строго на них, фактов не добавлять. Для каждой заметки:
- `tags`: 2–5 коротких тегов в нижнем регистре (слова через дефис, без `#`), по которым читатель стал бы искать; **не добавлять** теги домена `domain/…` (их ставит система);
- `links_out`: 0–4 заголовка **других** заметок из списка известных, символ в символ (дефисы тоже); не свой заголовок, не выдуманные, не URL; пустой список допустим;
- `abstract`: если в дайджесте `abstract: required` — резюме 2–4 предложения без списков, иначе `""`;
- ровно один элемент на заметку, `index` — номер в квадратных скобках.

Плюс `LANGUAGE_RULE`. Используется `roles/annotator.py`.

## 4. `llm/prompts/vault_analyst.py`

### `SYSTEM_INSTRUCTION: str`
Для «серой зоны» схожести (`role="vault_dedup"`). Вход — концепция из нового исследования и существующая заметка (заголовок, теги, краткое содержание). Решить: та же концепция (переиспользовать/дополнить) или самостоятельные (нужна новая). Главное правило: не плодить дубликаты; при сомнении между `reuse` и `distinct` выбирать `extend`. Плюс `LANGUAGE_RULE`. Используется `roles/vault_analyst.py::_resolve_ambiguous`.

### `FOLDER_SYSTEM_INSTRUCTION: str`
Распределение новых заметок по папкам (`role="folder_assignment"`). Вход — список существующих папок, папка по умолчанию, список заметок (заголовок + разделы). Для каждой: индекс и либо **точное** имя существующей папки (копировать символ в символ, не переводить и не менять), либо папка по умолчанию. Не придумывать новые папки. `LANGUAGE_RULE` не нужен (текстовых значений нет). Это не единственная защита: `_assign_folders_batch` проверяет результат кодом.
