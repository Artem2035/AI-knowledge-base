# Как добавлять и редактировать документацию

## Два рода документов — не смешивать

- **Reference-доки** — по одному файлу кода (или подпакету, см. правило
  ниже) на документ: классы, функции, параметры, возвращаемые значения,
  исключения. Справочник, открывается точечно.
- **Flow-доки** (лежат в `flows/`) — рассказывают процесс: что вызывается,
  в каком порядке, что течёт между вызовами. **Никогда** не повторяют
  таблицы параметров — только ссылаются на нужный reference-док.

Если пишете новый flow-док и ловите себя на копировании сигнатуры функции —
это сигнал, что деталь должна жить в reference-доке, а сюда — только ссылка.

## Структура папок

Документация зеркалит структуру пакетов кода:

```
docs/<пакет>/<файл>.md   ↔   <пакет>/<файл>.py
docs/<пакет>/_index.md   ↔   обзор всего пакета <пакет>/
```

Правила:

1. **Имя файла документации = имя файла кода** (без расширения `.py` →
   `.md`). Это единственная цель — открыть `Ctrl+P` → напечатать имя модуля
   → попасть в его доку, без похода в индекс.
2. **Каждая папка с более чем одним документом получает `_index.md`** — 1
   экран: назначение пакета, таблица «файл кода → документ», диаграмма
   зависимостей (кто вызывает пакет, что пакет вызывает), рекомендованный
   порядок чтения файлов внутри пакета.
3. **Маленькие модули можно объединять в один документ** — если пакет
   состоит из нескольких файлов, каждый из которых мал (условный ориентир —
   меньше ~50 строк содержательного кода, как `llm/prompts/*.py`), можно
   писать один документ на весь пакет. Обязательное условие: `_index.md`
   пакета явно называет объединённый файл и говорит, что он покрывает
   (см. пример в `llm/_index.md` про `prompts.md`). Без этой явной пометки
   объединение запрещено — иначе теряется предсказуемость «имя файла кода =
   имя документа».
4. **Не объединять документы только ради удобства писать** — если у файлов
   кода разный жизненный цикл, разные авторы или разный размер (один
   маленький, другой большой) — не объединять, даже если оба «в одной
   теме». Пример: `orchestrator/state_machine.py` и `orchestrator/budget.py`
   документируются РАЗНЫМИ файлами (`state_machine.md`/`budget.md`),
   несмотря на то что раньше были в одном `reference.md` — второй файл
   маленький и простой, но у него другой темп изменений и его логично
   открывать отдельно при работе с бюджетом лимитов, не читая весь
   `Orchestrator`.
5. **Осторожно с совпадением имён с точностью до подчёркивания** — если имя
   файла кода буквально `index.py` внутри пакета, у которого есть свой
   `_index.md` (пример: `vault/index.py` → `vault/index.md` рядом с
   `vault/_index.md`), явно предупредить об этом первой строкой в
   `_index.md` пакета.

## Относительные ссылки

Все кросс-ссылки — относительные пути от текущего файла (`../llm/core.md
§3`, а не абсолютные вида `docs_llm_core.md`). При переносе/переименовании
файла обязательно грепать репозиторий на упоминания старого пути:

```bash
grep -rln "старое/имя.md" docs/
```

и поправить все найденные вхождения — в этом проекте после каждого
переноса ссылки правились именно так (не автоматическим инструментом).

## Когда документ считается «завершён»

Reference-док в конце обязан:
1. Явно сказать «Документация по `<файл>` завершена.»
2. Дать одну ссылку «куда идти дальше» — либо на `_index.md` своего
   пакета, либо на следующий логичный документ (например,
   `llm/groq_client.md` в конце ссылается на `../flows/llm_cycle.md`).

## Обновление `README.md`

`README.md` в корне `docs/` — единственное место с полной картой «модуль
кода → документ» и списком пробелов. При добавлении/переносе/удалении
любого документа — обновить там: таблицу карты, дерево структуры (если
меняется), раздел «Пробелы и осознанно отложенное».

## Что НЕ документировать без явного запроса

На момент последней ревизии сознательно не документируются:
- `llm/router.py`, `llm/openrouter_client.py` — второй LLM-провайдер, вне
  текущего фокуса MVP.
- `roles/researcher.py`, `roles/extractor_critic.py` — активны только в
  `RESEARCH_MODE=web`, который сейчас заблокирован в коде.
- `retrieval/search.py` — решение о том, документировать ли, отложено (не
  исключено, что модуль будет удалён).

Не добавляйте им документы «на всякий случай» — если один из них снова
станет активным путём в коде, тогда и добавляем reference по тем же
правилам выше.
