# `storage/` — обзор пакета

> 1 экран: что лежит в `storage/`, кто с кем связан, куда идти за деталями.

## Назначение пакета

Единственный модуль со структурированными объектами, которыми обмениваются
этапы workflow (`Orchestrator → roles/* → validation/* → staging/*`).
Правило проекта: между ролями никогда не передаётся длинный "сырой" текст —
только эти типизированные Pydantic-модели. Это даёт валидацию на границах
между ролями, сериализацию в JSON для персистентности прогресса
(`staging/checkpoint.py`) и предсказуемый контракт для structured-output
вызовов LLM (`llm/schemas.py`, `../llm/schemas.md` — намеренно ОТДЕЛЁН от
этого пакета, см. там же).

## Файлы пакета → документы

| Файл кода | Документ |
|---|---|
| `storage/__init__.py` | — (пустой файл-маркер) |
| `storage/models.py` | `models.md` |

Пакет состоит из одного содержательного файла — отдельного `_index.md` с
диаграммой зависимостей достаточно, дробить `models.md` дальше некуда.

## Зависимости

```
roles/*.py, orchestrator/*.py, validation/*.py, staging/*.py, vault/*.py
        │  используют как общий язык данных
        ▼
storage/models.py  (Task, Plan, Evidence, DraftNote, StagingChangeset, TaskStatus, ...)
        │
        ▼
llm/schemas.py  — ОТДЕЛЬНЫЕ "выходные" Pydantic-модели под ответы LLM
                  (см. ../llm/schemas.md) — код-обвязка роли конвертирует
                  их в объекты storage/models.py, LLM никогда не заполняет
                  эти модели напрямую.
```

## Кто вызывает

Практически весь проект — это самый часто импортируемый модуль. В
частности: `orchestrator/state_machine.py` (`../orchestrator/state_machine.md`),
все `roles/*.py`, `validation/__init__.py`, весь пакет `staging/`.

## Порядок чтения

Один файл — `models.md`, читается целиком.
