# Документация: `llm/schemas.py`, `llm/prompts/*`, `llm/chunking.py`

> Три взаимосвязанных модуля "контракта" LLM-вызовов: `llm/schemas.py` —
> Pydantic-схемы structured-output (что модель ОБЯЗАНА вернуть),
> `llm/prompts/*` — статичные системные инструкции (что модели ГОВОРЯТ
> сделать), `llm/chunking.py` — как большие списки элементов режутся на
> батчи под токен-бюджет клиента ПЕРЕД тем, как попасть в промпт.

---

# Часть A. `llm/schemas.py` — контракты structured-output

**Назначение (из докстринга модуля).** Намеренно ОТДЕЛЕНЫ от
`storage/models.py`: LLM НЕ должна сама придумывать `task_id`/`path`/
`source_id` (это foreign keys, которыми управляет код) — вместо этого модель
ссылается на ИНДЕКСЫ элементов, переданных ей в промпте, а код-обвязка роли
уже сама подставляет реальные id/пути. Это снижает риск галлюцинаций в
структурных полях. Простые типы (`str`/`float`/`bool`/`list`) вместо
произвольных `dict` — потому что JSON Schema, которую LLM использует для
structured output, работает надёжнее с ФИКСИРОВАННОЙ формой полей.

Все классы ниже — `pydantic.BaseModel`, без собственных методов (чистые
схемы данных) — поэтому для каждого указаны только поля, а не
"параметры/возврат/исключения" в привычном смысле (валидация — стандартная
Pydantic, `ValidationError` при несоответствии типов).

# Часть B. `llm/prompts/*` — статичные системные инструкции

**Общий принцип модуля `llm/prompts/`** (см. докстринг `llm/prompts/outline_planner.py`):
статика (системная инструкция роли, не меняется от вызова к вызову в рамках
задачи) отделена от динамики (собирается в `roles/*.py` из конкретных
`Plan`/`Evidence`/`DraftNote` на каждый вызов). Это важно ещё и для Groq
prompt caching — ОДНА И ТА ЖЕ строка на все вызовы задачи не ломает кэш
(см. `llm/groq_client.py::CacheObservability`, `docs_llm_cycle_part3 §4`).

## B.0. `llm/prompts/__init__.py`

Пустой файл-маркер пакета.

## B.1. `llm/prompts/outline_planner.py`

### `OUTLINE_PLANNER_SYSTEM_INSTRUCTION: str`

**Описание.** Системная инструкция роли Planner (`role="outline_planner"`).
Ключевые правила (изложены в самом тексте инструкции):
1. Заметка = самостоятельная концепция, понятная без чтения других заметок —
   не дробить на заметки то, что имеет смысл только в контексте другой
   заметки (это подпункт, а не отдельная заметка).
2. Число заметок и подпунктов определяется ИСКЛЮЧИТЕЛЬНО полнотой темы — не
   подгонять под круглое число; если тема объективно требует много
   подпунктов в одной заметке (20-30) — не ограничивать себя искусственно
   (дальнейшая генерация текста по подпунктам НЕ зависит от их количества,
   т.к. `roles/elaborator.py` батчирует их отдельно, см. `llm/chunking.py`
   ниже).
3. Для каждого подпункта — короткое техзадание (`covers`), а НЕ сам текст.
4. Логическая последовательность подпунктов внутри заметки: определение/
   контекст → механизм → применение → ограничения/сравнение с
   альтернативами — используя ТОЛЬКО уместные для темы пункты, не подгоняя
   под шаблон.

Плюс языковое правило: отвечать на русском, кроме общепринятых технических
терминов (SQL, Python, RAG), которые не переводятся.

**Используется в:** `roles/outline_planner.py::build_plan`, как дефолт для
`system_instruction` параметра `generate_structured`.

## B.2. `llm/prompts/critic.py`

### `FEW_SHOT_EXAMPLES: str`

**Описание.** Приватная (по смыслу использования, не по имени — не
префиксована `_`) константа, конкатенируемая в конец `SYSTEM_INSTRUCTION`.
Содержит ДВА развёрнутых примера вердиктов, задающих "уровень строгости"
критика:
- **Пример 1 — `verdict='rewrite'`:** заметка с дублирующим по смыслу
  разделом ("Применение" пересказывает "Механизм" вместо сценариев
  использования) И придуманной точной цифрой ("снижает задержку на 40%"),
  не встречающейся ни в одном evidence — с образцом конкретного,
  адресуемого `feedback`.
- **Пример 2 — `verdict='ok'`:** заметка структурирована по заголовкам
  плана, факты отражены своими словами без искажений, конкретных чисел
  сверх evidence нет; МЕЛКАЯ стилистическая шероховатость — НЕ повод для
  `rewrite`.
- Ключевое отличие, явно проговорённое в тексте: `rewrite` — за КОНКРЕТНУЮ,
  адресуемую проблему; НЕ `rewrite` — за стилистические предпочтения, длину
  предложений, выбор синонимов.

### `SYSTEM_INSTRUCTION: str`

**Описание.** Системная инструкция роли Critic (`role="critic"`, ревью УЖЕ
НАПИСАННОЙ заметки — см. докстринг модуля, отличие от Critic внутри
`extractor_critic.py`, который сверял утверждения с ТЕКСТОМ ИСТОЧНИКА; здесь
сверять не с чем, ни в `RESEARCH_MODE=knowledge`, ни в текущей интеграции
для web — поэтому инструкция ограничивает критика тем, что реально можно
проверить БЕЗ внешней истины). Проверяет:
1. внутреннюю согласованность (нет ли противоречий внутри самого текста);
2. полноту относительно списка фактов (все ли значимые факты отражены);
3. структуру и ясность изложения (нет ли бессмысленных повторов, воды,
   оборванных мыслей, несвязанных разделов);
4. отсутствие ЯВНО добавленных точных деталей (чисел, дат, версий, названий),
   которых не было среди переданных фактов;
5. полноту покрытия заголовков (все заявленные планом разделы `##` должны
   присутствовать и быть содержательно раскрыты, а не оставлены формальными
   пустыми разделами).

Явно проговаривает: у критика НЕТ доступа к внешним источникам/интернету —
не пытаться проверять фактическую точность против реального мира, только
внутреннюю логику текста и его соответствие переданному списку фактов.

Итог: `verdict='ok'`, если заметка хороша; `verdict='rewrite'` с КОНКРЕТНЫМИ
замечаниями в `feedback` — если есть существенные проблемы; НЕ придираться
по мелочам — переписывание оправдано только при реальных проблемах, не ради
стилистических предпочтений.

`SYSTEM_INSTRUCTION = "..." + FEW_SHOT_EXAMPLES` (конкатенация в конце файла).

**Используется в:** `roles/critic.py::review_draft`.

## B.3. `llm/prompts/elaborator.py`

### `SYSTEM_INSTRUCTION: str`

**Описание.** Системная инструкция роли Elaborator (`role="elaborator"`,
только `RESEARCH_MODE=knowledge`). В отличие от Extractor, здесь НЕТ
входного текста источника — модель раскрывает подтему из СОБСТВЕННЫХ знаний.
Формулировка НАМЕРЕННО требует явно помечать неуверенность (в отличие от
`extractor_critic.SYSTEM_INSTRUCTION`, где Critic сверяет утверждение с
текстом источника — здесь сверять не с чем, поэтому инструкция прямо просит
модель быть ЧЕСТНОЙ про границы своей уверенности, а не имитировать
проверку, которой нет). Ключевые правила:
- раскрыть КАЖДЫЙ раздел ОТДЕЛЬНО, строго по техзаданию (`covers`), не
  путая материал разных разделов между собой, даже если они относятся к
  одной заметке;
- писать на русском, кроме общепринятых терминов (SQL, Python, RAG);
- **честность:** не выдумывать точные числа/даты/версии/статистику/имена
  авторов/названия публикаций, если не уверена модель — лучше сформулировать
  обобщённо, чем дать точную, но возможно неверную деталь;
- `confidence` оценивается ЧЕСТНО: высокий (>0.8) — только для устоявшихся,
  общеизвестных фактов; для деталей, которые могут быть неточными/спорными —
  снижать `confidence` и коротко пояснять в `critic_note`;
- если у раздела есть существенно разные трактовки/подходы в индустрии —
  отметить это явно, а не выбирать один вариант как единственно верный;
- каждое утверждение атомарно (одна мысль);
- для каждого факта указать `unit_index` — номер раздела в квадратных
  скобках, к которому он относится.

**Используется в:** `roles/elaborator.py::_elaborate_batch`.

концепция?" (`role="vault_dedup"`). Дана концепция/факт из нового
исследования и существующая заметка Vault (заголовок, теги, краткое
содержание). Определить: та же концепция (стоит переиспользовать/дополнить),
или разные, самостоятельные концепции (нужна отдельная новая заметка).
Главное правило, явно проговорённое: НЕ ПЛОДИТЬ ДУБЛИКАТЫ — если модель
сомневается между `'reuse'` и `'distinct'`, выбирать `'extend'` (дополнить
существующую заметку новым материалом).

**Используется в:** `roles/vault_analyst.py::_resolve_ambiguous`.

### `FOLDER_SYSTEM_INSTRUCTION: str`

**Описание.** Инструкция роли Vault Analyst для распределения по папкам
(`role="folder_assignment"`). Даны: список существующих папок Vault, папка
по умолчанию для темы, список НОВЫХ заметок (заголовок + разделы). Для
КАЖДОЙ заметки указать её индекс и папку — либо ТОЧНОЕ имя одной из
существующих папок (если тема заметки ей действительно соответствует), либо
папку по умолчанию, если ни одна не подходит. Явный запрет: НИКОГДА не
придумывать новые папки, которых нет в списке и которые не являются папкой
по умолчанию.

**Используется в:** `roles/vault_analyst.py::_assign_folders_batch`. Код
дополнительно ПРИНУДИТЕЛЬНО проверяет это правило после ответа (safety net,
см. `FolderAssignmentOutput` выше) — инструкция промпта НЕ является
единственной защитой от галлюцинированных папок.

## B.5. `llm/prompts/synthesizer_writer.py`

### `FORMATTING_GUIDANCE: str`

**Описание.** Вынесенный в ОТДЕЛЬНУЮ константу блок про форматирование
(Obsidian Flavored Markdown) — не вплетён единым куском в
`WRITE_SYSTEM_INSTRUCTION`, чтобы (а) его можно было переиспользовать
отдельно (например, для будущей роли "reformat existing note") и (б) чтобы
при правках форматирования не задевать остальную часть инструкции по
содержанию/ссылкам/языку. Принцип, явно проговорённый в докстринге модуля:
элементы форматирования (callout, списки, код) — это ИНСТРУМЕНТЫ ПО СМЫСЛУ,
а НЕ обязательный чек-лист на каждую заметку. Прежняя версия промпта
требовала фиксированную структуру (обязательный callout в начале,
обязательный нумерованный и маркированный список и т.д.) — из-за чего
модель добавляла притянутые списки из ОДНОГО пункта и пустые предупреждения
там, где по содержанию их не было (подгоняла материал под форму вместо
обратного) — эта проблема и стала причиной переписать промпт без
обязательных элементов.

Конкретное содержание: `> [!type] Заголовок` callout-ы (`abstract` — резюме
перед деталями, не для короткой заметки; `warning` — частая ошибка/неочевидное
поведение; `tip` — практический совет; `info` — важное уточнение контекста);
списки (нумерованный — только реальная последовательность шагов;
маркированный — перечисление однородных фактов/вариантов); `**жирный**` —
ключевые термины; `` `код` `` — имена функций/методов/путей; курсив —
смысловой акцент, умеренно; блоки ` ```язык ` — только для реально
иллюстрирующего примера; LaTeX (инлайн `$x^2$`, блок-формула двойными `$$`
на отдельных строках, НЕ оборачивать в ` ``` `) — только для объективно
математических/технических тем.

### `WRITE_SYSTEM_INSTRUCTION: str`

**Описание.** Системная инструкция роли Obsidian Writer (`role="synthesizer_write"`).
Ключевые правила:
- пишет ОДНУ заметку по плану (заголовок/action/папка заданы, НЕ обсуждаются);
  для `action='create'`: `tags`, `body_md`, `links_out`; для `action='update'`:
  `append_section` — только НОВЫЙ материал, НЕ повторять существующее
  содержимое;
- объём: целевой диапазон слов задаётся В ПРОМПТЕ (динамически, не здесь) —
  обычно ~1 страница; при заявленных 2 страницах структурировать через `##`,
  разделы выбирать по смыслу темы; если фактов меньше, чем нужно для
  объёма — писать короче и честно (минимум 3 содержательных абзаца), не
  растягивать повторами и неподтверждёнными деталями;
- + `FORMATTING_GUIDANCE` (вставлена f-строкой внутрь);
- ссылки (`links_out`) — только заголовки заметок Vault (НИКОГДА не URL),
  точно как в переданном списке (включая дефисы); ссылку на тему ВНЕ списка
  добавлять только если это самостоятельная концепция, не на каждый
  незнакомый термин;
- ЗАПРЕЩЕНО: свой раздел/предложение "См. также"/"Related notes" внутри
  `body_md`/`append_section` — секцию "## Связанные заметки" система
  формирует САМА из `links_out` (`tools/markdown_tools.py::render_markdown`),
  дублирование ломает вывод; другие ключи YAML frontmatter (кроме
  `title`/`tags`/`created`) — не предлагать, система их игнорирует
  (`_ALLOWED_FRONTMATTER_KEYS`);
- язык: русский, кроме общепринятых терминов; НЕ копировать текст источника
  дословно — пересказ своими словами с указанием источника факта.

**Используется в:** `roles/synthesizer_writer.py::write_note`, как дефолт
для `system_instruction`, если вызывающий код (`Orchestrator`) не подставил
кастомный вариант (см. `MERGE_AWARENESS_GUIDANCE` ниже).

### `MERGE_AWARENESS_GUIDANCE: str`

**Описание.** Добавляется к `WRITE_SYSTEM_INSTRUCTION` ТОЛЬКО когда
`settings.enable_draft_merging=True` (см. `orchestrator/state_machine.py::run`,
переменная `write_system_instruction`). Writer НЕ ЗНАЕТ, с КЕМ КОНКРЕТНО
заметка будет объединена (это решается пользователем только в самом конце,
см. `staging/draft_merge.py`), но может заранее писать так, чтобы
объединение с ЛЮБЫМИ соседями по плану проходило чище. НЕ устраняет риск
СОДЕРЖАТЕЛЬНОГО пересечения тем (для этого модель должна была бы видеть
текст соседних заметок), но снимает самый частый и самый заметный источник
"склеенности" — шаблонные вступления/заключения и повтор общего определения
темы плана в каждой заметке. Конкретные правила:
- НЕ писать шаблонное вступление ("В этой заметке рассмотрим...") или
  заключение ("Подводя итог...") — при объединении с соседними разделами
  такие фразы повторяются на каждый раздел и выглядят избыточно;
- если заметка предполагает БАЗОВОЕ определение общей темы плана — дать его
  КОРОТКО, одной фразой, и сразу переходить к специфике именно ЭТОЙ
  заметки, а не темы в целом (разворачивать общее определение — задача
  заметки, посвящённой самой теме, а не каждого её аспекта);
- оставаться строго в рамках заявленного заголовка, не отклоняться в
  объяснение смежных концепций — по плану им, скорее всего, посвящены
  отдельные заметки.

Один и тот же СТАТИЧНЫЙ вариант системного промпта на ВСЮ задачу (не
зависит от того, реально ли пользователь потом что-то объединит — только от
того, что такая возможность ВКЛЮЧЕНА) — важно для Groq prompt caching (см.
общий принцип модуля выше).

# Часть C. `llm/chunking.py` — батчинг элементов под токен-бюджет

**Назначение (из докстринга модуля).** Общая утилита для деления списка
элементов на батчи под доступный prompt-бюджет клиента. Нужна, чтобы
избежать silent auto-truncate (`GroqClient._auto_truncate_prompt` режет
промпт С КОНЦА — для списков кандидатов это означает потерю "хвостовых"
элементов ДО ТОГО, как их вообще увидела модель). Для клиентов БЕЗ
`available_prompt_budget_tokens()` деление не нужно — возвращается один
батч со всеми элементами, поведение не меняется.

## C.1. `split_items_into_batches(items, *, client, system_instruction, response_model, render_item, static_overhead_text="") -> list[list[T]]`

**Описание.** Универсальный батчер по ЧИСТО ТОКЕННОМУ бюджету:
1. Если `items` пуст — возвращает `[]` немедленно.
2. `budget_fn = getattr(client, "available_prompt_budget_tokens", None)` —
   если у клиента НЕТ этого метода вообще (`None`) — возвращает ОДИН батч со
   всеми элементами (`[list(items)]`), без деления.
3. `available_tokens = budget_fn(system_instruction, response_model)` — если
   `None` (например, `RoleRoutingLLMClient` без делегирования, см.
   `docs_llm_cycle_part1_orchestrator.md §5`) — также ОДИН батч без деления.
4. `overhead_tokens = estimate_tokens(static_overhead_text)`,
   `text_budget_tokens = max(available_tokens - overhead_tokens, 0)`.
5. Если `text_budget_tokens <= 0` — бюджета не хватает даже без элементов —
   КАЖДЫЙ элемент идёт ОТДЕЛЬНЫМ батчем (`[[item] for item in items]`),
   дальше клиент сам решит (auto-truncate/ошибка), но хотя бы НЕ теряется
   весь список сразу.
6. Иначе — жадный проход по `items`: накапливает `current` батч, суммируя
   `estimate_tokens(render_item(item))`; если добавление ОЧЕРЕДНОГО элемента
   превысило бы `text_budget_tokens` (и текущий батч уже НЕПУСТ) — текущий
   батч закрывается, начинается новый.

**Параметры:**
| Имя | Тип | Назначение |
|---|---|---|
| `items` | `Sequence[T]` | Элементы для батчинга (кандидаты источников, единицы извлечения, подпункты и т.п.). |
| `client` | LLM-клиент (keyword-only) | Источник `available_prompt_budget_tokens(...)`. |
| `system_instruction` | `str` (keyword-only) | Передаётся в `available_prompt_budget_tokens` для оценки накладных расходов схемы+системы. |
| `response_model` | `type[BaseModel]` (keyword-only) | Класс ожидаемого ответа — его JSON Schema тоже занимает токены. |
| `render_item` | `Callable[[T], str]` (keyword-only) | Как отрендерить ОДИН элемент в текст для оценки его размера в токенах. |
| `static_overhead_text` | `str` (keyword-only, дефолт `""`) | Дополнительный СТАТИЧНЫЙ текст промпта (не зависящий от батча), который тоже занимает токены — например, преамбула с темой задачи. |

**Возвращаемое значение:** `list[list[T]]` — список батчей, сохраняющих
исходный порядок элементов.

**Исключения:** не поднимает — деградирует до "один элемент = один батч" в
худшем случае, а не падает.

**Кто вызывает:** `roles/researcher.py::select_relevant_sources`,
`roles/extractor_critic.py::extract_evidence_from_sources` (внутри, ДО
`batch_for_quality_and_budget` в `elaborator`), `roles/vault_analyst.py::_assign_folders_batch`.

## C.2. `batch_for_quality_and_budget(items, *, client, system_instruction, response_model, render_item, static_overhead_text, max_items_per_batch) -> list[list[T]]`

**Описание.** Комбинирует ДВА НЕЗАВИСИМЫХ предела на размер батча:
1. токен-бюджет (`split_items_into_batches` — как выше);
2. КАЧЕСТВЕННЫЙ потолок `max_items_per_batch` — НЕ про бюджет, а про то, что
   при БОЛЬШОМ числе элементов в одном вызове модель скатывается в
   однострочные поверхностные ответы на каждый (например, заметка с 30
   подпунктами в одном вызове).

Реализация: сначала `split_items_into_batches` делит по токен-бюджету
(`budget_batches`), затем КАЖДЫЙ полученный батч дополнительно нарезается
`range(0, len(batch), max_items_per_batch)` кусками не больше
`max_items_per_batch`.

Порядок элементов сохраняется, поэтому границы батчей ЧАЩЕ ВСЕГО совпадают с
границами заметок. Исключение (явно проговорено в докстринге функции): если
шаг (1) уже разрезал ПОСЕРЕДИНЕ заметки по бюджету (при длинных элементах) —
тогда шаг (2) режет уже этот кусок, и последний под-батч может оказаться
короче `max_items_per_batch`. Для коротких `heading+covers` (типичный случай
`ElaborationUnit`) это практически не происходит.

**Параметры:** те же, что у `split_items_into_batches`, ПЛЮС:
| Имя | Тип | Назначение |
|---|---|---|
| `max_items_per_batch` | `int` (keyword-only) | Качественный потолок элементов на один вызов. Из `settings.max_subpoints_per_generation_batch` (дефолт `6`). |

**Возвращаемое значение:** `list[list[T]]` — финальные батчи, каждый не
длиннее `max_items_per_batch` (кроме описанного выше редкого исключения на
границе токен-разреза).

**Исключения:** те же, что у `split_items_into_batches` (не поднимает).

**Кто вызывает:** ИСКЛЮЧИТЕЛЬНО `roles/elaborator.py::elaborate_outline`
(единственное место в проекте, где используется ДВОЙНОЕ ограничение —
`extractor_critic`/`researcher`/`vault_analyst` используют только
`split_items_into_batches`, т.к. у них нет отдельного "качественного"
потолка на число элементов в батче, только токенный).

## Сводная схема: путь одного батча от плана до промпта

```
roles/elaborator.py::elaborate_outline(plan, client, status, ...)
        │
        ▼
build_elaboration_units(plan, already_done_subpoint_ids)  ── list[ElaborationUnit]
        │
        ▼
llm/chunking.py::batch_for_quality_and_budget(
    units, client=client,
    system_instruction=llm/prompts/elaborator.py::SYSTEM_INSTRUCTION,
    response_model=llm/schemas.py::ElaborationOutput,
    render_item=lambda u: f"{u.note.title} :: {u.subpoint.heading}\n{u.subpoint.covers}",
    static_overhead_text=...,
    max_items_per_batch=settings.max_subpoints_per_generation_batch,
)
        │
        ▼  для каждого батча
_elaborate_batch(batch, plan, client, status)
        │
        ▼
client.generate_structured(
    role="elaborator",
    prompt=<нумерованный листинг батча>,
    response_model=llm/schemas.py::ElaborationOutput,
    status=status,
    system_instruction=llm/prompts/elaborator.py::SYSTEM_INSTRUCTION,
)
        │
        ▼
llm/groq_client.py::GroqClient.generate_structured(...)  ── см. docs_llm_cycle_part3
        │
        ▼
ElaborationOutput  →  список storage/models.py::Evidence (через unit_index)
```
